Does AutoCodeBench-V2 show an Elixir advantage?

Independent audit of the February 17, 2026 release, completed November 21, 2026.

1. Executive verdict

AutoCodeBench-V2 does not establish that Elixir is the best language for LLM coding. Its public leaderboard does not establish that Elixir ranks first in V2, either. The nine published bars are overall model averages. The widely cited Elixir scores come from the original 3,920-task AutoCodeBench-Full. The February V2 release uses separate language-specific problem sets and supplies neither language scores nor a model-by-task outcome matrix. February V2 chart · August 2025 paper · ICLR version, Table 4

The task audit found unequal task composition and concrete grading defects. Several Elixir tasks have fewer essential steps than nearby examples in Python, Rust, Java, or C++. Other Elixir tasks are comparably demanding or harder, and some similarly labeled tasks in other languages are straightforward. The findings rule out treating the language sets as difficulty-equivalent. They leave the net bias, an Elixir-specific effect size, and the performance ranking unidentified. Independent matched comparisons provide counterexamples to a general Elixir advantage. Pinned February task and test data

Confidence is high about what the leaderboard measures and about the specific task and test differences below. Confidence is moderate that the February Elixir set has a narrower reasoning burden than several focal comparison sets in some common task families. The audit has insufficient evidence to rank average intrinsic difficulty across all 20 languages, estimate how much scoring defects changed any model's V2 result, or identify the best language for repository work.

3. Evidence of unequal task difficulty

Full-file measurements and a topic sample

  • Across all 998 items, Elixir has the shortest median statement at 275 whitespace-delimited words. Its median stays at 264.5 after fenced code is removed, versus 388 for Python, 297.5 for Go, 307 for TypeScript, 340 for JavaScript, 491.5 for Rust, 550 for Java, and 609 for C++. The Elixir references are also shorter than those for these seven languages, with 46 nonblank lines at the median. Julia, Perl, Racket, and Shell have shorter references than Elixir. Boilerplate, typing, standard-library functions, comments, and coding styles all affect these counts. Prompt length can reflect extra requirements or extra explanation. February data
  • The February labels put 30 of 50 Elixir items in “hard,” versus 42 of 53 Python and 43 of 50 Rust, but just 26 of 50 Java. Only two Elixir items are “easy,” compared with seven Python, nine Go, and eight TypeScript. The labels are poor evidence for equivalence. For example, the “hard” Elixir maximum-subarray problem and “easy” Java timed, bounded, thread-safe queue differ considerably in the number and kind of requirements. A blind human study could score these dimensions independently. February data, rows 193 and 256
  • The Python references import NumPy in seven tasks, Pillow in one and scikit-learn in one, by a static parse of all 53 outputs. No Elixir reference uses Mix.install/1. That is a dependency indicator and does not establish which packages the sandbox preloads or what a prompt requires. The Elixir prompts still include language-specific requirements such as Unicode grapheme segmentation, Erlang term order for deterministic BFS, structs, atoms, and string-conversion protocols. February data

I drew a reproducible 12-row simple random sample within each of the eight focal languages and coded one dominant topic per prompt. “Discrete” includes tree, graph, and combinatorial problems. “Application” includes state machines, application interfaces, and simulations. “Numerical” includes scientific or numerical modeling. “Text/data” includes representation and serialization. The seed and 96 row labels are in analyze.py. This was a single-reviewer, unblinded topic audit. Mixed-topic classifications depend on the rubric. Elixir 161 / Python 559, Tic-Tac-Toe Elixir checks eight fixed winning lines and distinguishes a draw from an ongoing board. Python checks terminal states, searches for an optimal move, accepts equivalent optima, and must preserve the input board. Both are labeled hard and the Python statement is shorter.
Elixir 160 / C++ 9, Kalman filters Elixir supplies scalar prediction and update formulas and needs one map and a pair of scalar estimates. C++ supplies a nonlinear motion and observation model, a 3×3 covariance, angle wrapping, and landmark updates. The extra matrix and boundary reasoning would survive a port.
Elixir 159 / C++ 29, camera projection Elixir computes one 3×4 matrix following a specified homography decomposition, normalization and orientation convention. C++ additionally implements transformation factories, matrix composition, camera view and projection, and point transformation. Elixir still needs matrix inversion, cross products and numeric tolerance.
Elixir 169/190 / Rust 750, land components Elixir counts 4-connected components and returns one integer. Rust handles 8-way adjacency, per-seed area, enumeration, maximum, and whole-grid connectivity with mutable visitation state. The Rust prompt is labeled medium while both Elixir rows are hard.
Elixir 169/190 / Rust 796, flood fill Rust adds caller-selected topology, mutation of the supplied image, initial and replacement colors, and counts and percentages. Both use grid traversal. Rust specifies invalid seeds, empty grids, and same-color behavior, with more observable outputs per call.
Elixir 165 / Rust 792, graph analysis Elixir builds an undirected graph and does BFS with sorted neighbors and explicit absent-start behavior. Rust handles directed reachability, all mother vertices, strongly connected components, invalid indices, and deterministic results. The Rust task requires a different graph analysis.
Elixir 171 / Rust 765, search trees Elixir specifies insertion with replacement, lookup, min, max, and floor. Rust additionally needs removal, copying, multiple traversal orders, and invariant checks. Ownership adds implementation burden, and deletion and traversals add requirements in any language.
Elixir 171 / TypeScript 953, search trees The direction reverses. TypeScript specifies insert, lookup, and height, plus chaining and exact node shape. Elixir adds key-value replacement, extrema and floor. A TypeScript class by itself does not imply greater algorithmic difficulty.
Elixir 186 / Java 288, tree diameter Elixir returns the maximum edge count for a binary tree. Java reconstructs an endpoint-to-endpoint path in an N-ary tree. Both require combining subtrees, with Java carrying path information and handling arbitrary child degrees.
Elixir 183 / C++ 39, interval queries Both count inclusive interval coverage per query. Elixir leaves the method open and suggests up to 100,000 intervals and queries. C++ explicitly requires a lazy segment tree and supporting operations. Elixir's nine assertions use small input counts, including large coordinate values. The C++ suite also has small functional checks and does not verify the submitted algorithm uses a segment tree.
Elixir 194 / Go 248, balanced binary tree Same every-node height predicate with an empty-tree success case. Elixir uses tuples and Go pointer-linked nodes. Both are labeled easy. The full suites differ in tree shapes and coverage, even where the functions could share one oracle.
Elixir 156 / TypeScript 996, chess move validation Elixir handles a board map, turn ownership, multiple piece rules and path restrictions. TypeScript specifies one bishop rule, path blockage and own-color occupancy. Elixir's full suite tests only two rejected pawn moves. The Elixir task is broader on paper and narrower in what its suite enforces.
Elixir 193 / C++ 8, sequence optimization Maximum subarray needs a one-pass recurrence, including all-negative and empty inputs. C++ wiggle analysis requests several local statistics plus any one longest alternating subsequence in original order. Both are hard by label.
Elixir 153 / Rust 795, text formatting Elixir packs words and distributes spaces with left bias and separate final-line rules. Rust applies ordered punctuation, capitalization, and spacing rules and must count corrections. These are distinct types of reasoning. Neither prompt reduces to a library call.
Elixir 177 / TypeScript 998, permutations Elixir enumerates all permutations, preserves multiplicity, handles empty input, and uses grapheme clusters or printable list values. TypeScript computes a single lexicographic successor for a small ASCII alphabet, including the terminal ordering case. Neither task is a translation and their algorithmic costs are not comparable by reference length.

Elixir also includes wildcard decoding at up to 100,000 characters (#195), a bin-packing task that asks for optimality on the supplied cases (#179), Shamir share generation and reconstruction (#188), and a maximum-number merge challenge (#196). Those ask for dynamic programming, combinatorial optimization, or modular arithmetic even when expressed compactly. At the other extreme, the 4-connectivity island pair #169 and #190 shares a task family and a function signature within Elixir itself. Duplicating such families reduces effective diversity and can give related reasoning or failure modes extra weight. The audit establishes imbalance in composition, specification burden, and some grading coverage. It cannot estimate any language's overall latent task difficulty. February data

4. Benchmark methodology audit

V2 reused Full’s selected problems and difficulty labels. Tencent describes V2 as a refinement of the original dataset using unspecified top proprietary models and a sandbox. To identify the exact source, I joined each V2 row’s decoded (language, signature) to Full’s (language, canonical_solution) by exact string equality. Every December row (1,000/1,000) and every February row (998/998) resolves to one distinct Full row. Every joined row has the same difficulty label as its Full parent. Every joined question and full test field differs in exact text, which can include formatting changes. This establishes Full ancestry and label carryover, even though the edited specifications and tests can change what a task requires. For example, February Elixir line 149 (largest values in a BST) maps to Full line 1693 and Elixir line 150 (largest histogram rectangle) maps to Full line 1615. V2 release documentation · Full release · December V2 release · February V2 release

Python, Java, C++, JavaScript, Go and Shell used the direct path. The sandbox provided expected outputs, and the generator assembled tests and wrote the user-facing task from solution and tests. Published generation code drops unsuccessful executions. Full difficulty, quality and diversity gates DeepSeek-Coder-V2-Lite generated ten samples per candidate. A perfect 10/10 removed it. Surviving labels are hard for 0/10, medium for 1–5/10 and easy for 6–9/10. DeepSeek-R1-0528 checked specification/test consistency, and DeepSeek-V3-0324 labeled categories for cyclic sampling. The paper reports 25.1% removal at the difficulty gate for Python. It attributes the unusually high scores of strong models on some low-resource languages to easy candidates escaping this filter. It provides neither a controlled Elixir–Python estimate of this effect nor Elixir’s rejection denominator. The paper’s manual validation covered Python, C++, Java, JavaScript, Go and Shell. Full → V2 The two public releases allow measurement of which Full survivors were retained and which fields changed. The available V2 methodology provides no refiner identities, model-to-language assignments, prompts, candidate rankings, thresholds, validation failure logs, independent difficulty judgments, or selection rationale for refinement-stage drops. Iterative refinement can introduce differential selection or change requirements, but its impact remains unidentified. V2 release documentation · Public dataset files

The Full-to-February selection was not uniform over inherited labels. Elixir retained 2/13 easy, 18/46 medium and 30/139 hard Full tasks. Python retained 7/36 easy, 4/26 medium and 42/134 hard tasks. That yields 36% medium and 60% hard in V2 Elixir versus 7.5% medium and 79.2% hard in V2 Python. Rust retained 0/8 easy, 7/38 medium and 43/153 hard. TypeScript retained 8/23 easy, 4/26 medium and 38/150 hard. These are exact selection rates among released Full tasks. They show how V2 changed the inherited mix without equating difficulty across languages. In particular, Elixir retained a smaller share of its easy-labeled pool than Python did. A story in which V2 simply chose more easy-labeled Elixir questions fits these counts poorly. The earlier weak-filter mechanism remains plausible precisely because a label such as hard can reflect filter-model failure in expressing a simple solution. Full release · February V2 release · Paper, Table 3

Direct test of the filter hypothesis. The ancestry join confirms that V2 inherits survivors of the potentially biased gate and uses its labels. Testing how many equally easy problems slipped through requires the rejected pool. Obtain source-to-translation IDs, all candidate versions including failures, exact model revisions and prompts, all ten completions, per-attempt grader outcomes, prefilter counts, Critic decisions, category sampling decisions and V2 refinement acceptance logs. Take a stratified random sample of prefilter candidates, create independently checked Python/Elixir versions of each specification, and execute DeepSeek-Coder-V2-Lite with the original decoding settings and a common semantic oracle. Estimate the paired difference in 10/10 removal rates among independently easy tasks. Separately report prompt extraction, compilation, runtime and semantic failures. Paired resampling by source task preserves dependence. Replay the downstream gates under the original filter, a separately calibrated multi-model filter and an independently rated filter, then compare which difficulty distributions and score gaps survive. With public data alone, this experiment can be reconstructed on newly authored tasks to test the mechanism, while historical error rates and causal effects on V2 require the original logs.

Full (3,920 tasks), Lite (1,586 selected for prior model solvability) and Complete (1,000 Lite-derived three-shot completion tasks) are separate from December V2 (1,000) and February V2 (998). AutoCodeInstruct’s Qwen filters concern a training dataset. Neither its thresholds nor Lite’s model-solvability selection describe V2 construction. ICLR paper, §2.2 and §4 · Tencent release list

5. Evaluation and sandbox audit

Known-wrong answers passed grading on nine of 50 Elixir tasks. Each affected test function prints comparisons but lets the process succeed after a mismatch. I kept the test suites intact, deliberately changed task answers, and checked both the public V2 sandbox service and a native replay. Each confirmed false pass printed a mismatch, exited with code 0, and printed the completion marker. The published service returned PASSED. The nine tasks could account for up to 18 percentage points of a model's Elixir score if a stricter grader flipped all nine of its answers. The observed effects on the leaderboard models remain unknown. February dataset, pinned evaluation client, pinned sandbox image

Assertions alone also leave important gaps. At #156 the entire chess suite is two invalid moves. An always-invalid implementation passes when the module declarations are preserved. An added e2→e3 positive test rejects it and accepts the supplied implementation. #183 accepts a brute-force solution that scans every interval for every query. The problem extends beyond Elixir. A Perl #473 function returning an empty string passed its print-only checks. The test emits uppercase FAILED and the image's Perl matcher looks for lowercase failed. Ruby #699 prints its atoi comparisons and accepted an always-zero implementation. Markdown extraction also produces false negatives. The V2 client takes the first fenced code block, removes text through the last closing reasoning tag when present, and makes an Elixir-only rewrite. It replaces a first-line module declaration with the first line from signature, or wraps module-body code using that declaration. This can rescue a bare function or a wrong module name. It also rejects a legitimate module layout at #156. The supplied answer declares Chess.Piece, Chess.Board, then Chess. The extractor renames the first module to Chess, making Chess.Piece undefined at compile time. The unmodified code passes the original tests and the additional correct-move assertion. Go #207 exposed a second verified harness collision. Its February test code declares the ring-buffer type, constructor, and methods requested of the candidate. The official Go splicer combines both bodies after import processing. The service rejected both released implementations with duplicate declarations. The V2 output also produced undefined errors references. The nearby #248 Go control accepted its implementation and rejected its always-false mutant after the container’s build cache was warm. V2 client, February dataset, published sandbox layers

Execution and numeric strictness. I retrieved the image's published source and configuration layers, including code_config.yaml, code_splicer.py, executor.py, and code.py. In the benchmark's function-plus-test mode, the client submits the extracted code and the entire public full_test_func, and checks for a sandbox pass and the marker in stdout. The Elixir runner concatenates both sources, invokes elixir test.ex, and checks resource errors, nonzero status, and the case-sensitive phrase assertion fails. Its pass decision does not interpret boolean or arbitrary failure output. Go uses go test -v, Rust cargo test -- --nocapture, TypeScript npx tsx, C++ g++ then a native executable, Python python3, JavaScript node, and Java a JVM worker. The client requests 30 seconds and waits 60 seconds for HTTP. The image honors the timeout request, with separate compilation and execution phases in some runners. The focal languages use a configured 20,480 MB memory default. The subprocess source says CPU percentage enforcement was removed. Runtime initialization, native compilation, dependency caches, and per-language stderr/stdout rules still differ. Equality and exception expectations live in the suite, including Elixir's == numeric equivalence for integer and float and its task-specific floating tolerances. There is no single numeric oracle shared across these V2 language sets. The publicly downloadable tests are hidden from the documented inference prompt. The audit could not establish the presence of any extra publisher-only tests. V2 client, sandbox layers, Elixir equality documentation

6. Difficulty-controlled evaluation protocol

I did not generate matched completions for the nine February leaderboard configurations. The public files lack those runs and this environment has no configured model API credentials for them. The native and official sandbox probes in §5 evaluate grading only. The closest executed independent model comparisons are in §8.

  1. Sample semantic tasks. With seed 260217, group the 998 rows by underlying problem family before sampling. Mark near duplicates such as #169/#190 and #194/#248. Sample approximately 240 unique families, aiming for 12 from each source language with a prespecified topic and scope mix. Publish the sampled IDs, exclusion reasons, and source origin. A task that requires an ecosystem-specific framework may be impossible to port faithfully and should count toward separately reported portability attrition. Keep such tasks for an ecosystem-specific experiment. Include a separately reported held-out set of new tasks to probe recognition of public problems.
  2. Freeze a neutral specification and oracle. Preserve functional requirements, constraints, valid input domain, exception semantics and allowed outputs. Give two independent reviewers the original and target contracts with outcome data hidden. Have them certify requirements line by line and adjudicate disagreements. Include at least one reviewer familiar with the target language. Where the original is underspecified, publish the clarification before inference and have reviewers approve it for all languages. Use one language-neutral oracle and shared fixtures, plus boundary cases, property-based comparisons against a simple oracle and mutation checks. For the #194/#248 pilot, express the tree as nullable nodes with two children and 32-bit values, impose the same size cap, and add trees where only a deep descendant is imbalanced. Generate native tuples, pointers or objects in the harness. The model writes the tree predicate and receives the same information about the adapter in every language.
  3. Make runtimes comparable. Pin images, toolchains, library versions, CPU and memory. Use equivalent default libraries and allow idiomatic internal abstractions. Define Unicode, integer overflow, ordering, floating-point tolerance, ties, exception mapping and mutability before generation. Compile and run known answers and intentionally defective references for every adapter. Report both a common resource budget and a reference-calibrated sensitivity check for startup or interpreter overhead. Keep stdout for diagnostics and an out-of-process judge for verdicts.
  4. Cross tasks, languages and models. Generate for all 20 languages on each portable problem, with the eight focal languages as the primary analysis. Select several model families and both stronger and weaker configurations. Freeze checkpoint, temperature, effort, token and wall-clock limits, tool access, context and prompts. Gate any retries on logged infrastructure errors only. Specify one draw per task and language for Pass@1. For Pass@k, preregister k and the number of draws, keep all completions, and use 1 - choose(n - c, k) / choose(n, k) for c correct out of n draws when the sampling design warrants it. Run separate arms for first attempt and feedback-enabled repair. Pass@k estimator, Chen et al.
  5. Publish paired outcomes and stage-specific failures. 7. Statistical conclusions

  • The finite-corpus quantities in §§2–3 are exact for these files. Prompt length is a measurable property. As a descriptive sensitivity analysis, 4,000 within-language task resamples gave 95% percentile intervals for the Elixir median word gap of about −161 to −72 against Python, −287 to −178 against Rust, and −91 to +14 against Go. These are conditional on independently resampling the released rows. Shared task templates and the nonrandom pipeline limit any generalization, and the intervals measure words only.
  • The missing V2 outcomes make even crude performance comparisons inestimable. Neither a language-level interval nor difficulty-stratified performance, topic adjustment, language rankings, exclusion sensitivity, or regression of V2 correctness can be recovered from model totals. A finite-set score is exact given frozen grades. As a scale example for extrapolating from 50 independent tasks, 40/50 successes give a Wilson 95% interval of about 67–89%. Task-family clustering, inherited tasks and reused model families make treating the 50 or the nine model configurations as independent replicates especially misleading. Wilson interval reference, NIST
  • If the missing grades become public, first report per-model observed language differences on the released sets and resample task clusters with all model results paired within each cluster. Analyze model strength using scores on a held-out set or an overall score excluding the compared languages, so the subgroup definition does not leak the answer. Compare task-weighted, equal-language, equal-model, equal-family, median-model and leave-one-out summaries. Stratify by topic, review-rated difficulty, and verifier strength, with overlap checks and family-clustered intervals. A regression can describe residual differences after measured adjustments. Because each original task appears in only one language, a fixed task effect would be collinear with language. No observational adjustment can recover the paired counterfactual without stronger assumptions or matched variants.
  • The error distribution is also unavailable for V2 model runs. The known-answer and mutant probes can diagnose harness behavior and missed requirements. They cannot show what fraction of real failures came from invalid syntax, wrong algorithms, timeouts or runtime problems. Avoid labeling an official model's failure without its code, extracted source and execution trace.

9. Real-world implications

Elixir gives models compact ways to express common transformations. Immutable data limits mutation and aliasing across stages. Pattern matching and guards make data shape and cases explicit. The pipe operator and consistent collection operations such as Enum.map/2, Enum.filter/2 and Enum.reduce/3 can express processing steps in their execution order. Mix, formatting conventions, compiler diagnostics, ExUnit, and documentation with doctests can provide useful guidance to an agent with tool access. These are plausible mechanisms, and José Valim's account describes their rationale. The V2 benchmark does not hold the task fixed or experimentally vary any of them. Elixir documentation, pattern matching, collection APIs, documentation and doctests, Valim's explanation.

Python has comprehensions, generators, itertools and functools. TypeScript can give an agent narrowing and exhaustiveness feedback with discriminated unions. Rust provides pattern matching and ownership diagnostics, with a learning cost around borrowing and lifetimes. Go offers standard formatting and conventional explicit errors. Strong static feedback can help iterative repair even if it raises the bar for a passing first answer. The relative value depends on the project, checked rules, and agent access to build and test tools. Python functional programming guide, TypeScript narrowing, Rust ownership, Effective Go.

Unfamiliar syntax and idioms, less public training material, and narrower domain-specific libraries are plausible disadvantages. Actual frontier training mixtures are undisclosed in the cited experiments. Tokenizer and documentation interventions show that familiarity and access to context can matter without identifying an independent training-volume or language-design effect. Elixir's macros and framework DSLs, Phoenix and Ecto conventions, and OTP message ordering and supervision add reasoning demands that a pure transformation rarely exercises. A GenServer provides standard callbacks and supervision integration, and correct timeouts, lifecycle, state recovery and races still depend on the implementation. ACL tokenizer study, documentation-tool study, Elixir macros, GenServer, Ecto.

V2 supplies no empirical reason to switch an existing Python, TypeScript, Go, or Rust project to Elixir for agent productivity. For a greenfield system where Elixir already fits the workload and team, independent experiments show that some frontier agents can do substantial Elixir work. A productivity claim would require comparing time to accepted changes, regression rates, review and repair time, and operating cost across equivalent work including repository navigation, dependency changes, debugging, multi-file refactors, and maintenance. A one-shot function pass rate measures only part of that work. Longtail-SWE task design, Sweat Bench v6 methodology and results.
